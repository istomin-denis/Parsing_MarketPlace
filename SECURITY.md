# Безопасность и подготовка к аудиту

## Уже реализовано в прототипе

- Пароли хешируются через bcrypt с cost factor 12.
- Сессии хранятся на сервере в PostgreSQL; cookie имеет `httpOnly` и `sameSite=lax`. Для state-changing запросов проверяется `Origin` (если браузер его передал).
- В production cookie получает флаг `secure`.
- После входа/регистрации сессия регенерируется.
- SQL-запросы используют параметры, а не конкатенацию пользовательского ввода.
- ID пользователя берётся из серверной сессии, а не из тела запроса.
- Удаление истории ограничено одновременно `id` записи и `user_id` владельца.
- Входные данные проверяются Zod; JSON body ограничен 32 KB.
- Используются Helmet и rate limiting.
- Секреты вынесены в окружение; `.env` исключён из Git.

## Что ещё требуется проверить

Это не полный аудит и не гарантия отсутствия уязвимостей. Перед production-развёртыванием проверьте:

- CSRF-модель и поведение cookie при реальном домене/HTTPS.
- Политику паролей, защиту от перебора и восстановление доступа.
- Управление сессиями, истечение и отзыв сессий.
- XSS и безопасный вывод любых данных из внешних источников.
- SSRF, если появится возможность задавать URL источника.
- Ограничение частоты на уровне пользователя и IP.
- Логи, мониторинг, резервные копии и права PostgreSQL.
- Утечки секретов в текущей и прошлой истории Git.
- Зависимости, лицензии и обновления безопасности.

## Правила безопасной публикации

- Используйте только тестовые аккаунты и синтетические данные.
- Не коммитьте `.env`, дампы БД, session cookies, API keys и реальные персональные данные.
- Перед публичным раскрытием найденных проблем получите разрешение владельца приложения.
- Не публикуйте подробности неисправленных уязвимостей работающего сервиса.
- Описывайте только фактически выполненные проверки и подтверждённые результаты.
